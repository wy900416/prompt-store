# 最小改动纪律

评审成本由 diff 大小决定，不由改动质量决定。默认自己写下的是"待评审的补丁"，不是"最终代码"。

## 动手前

1. 用一句话写清"这个改动要解决的问题"，写不出来就不要动代码。
2. 确认改动点：`文件:行号`，以及它被谁调用。
3. 如果发现三处以上需要改，停下来先说明为什么不是一处的问题。

## 改动中

- 只改达成目标必需的行。顺手发现的其它问题记下来，不要改。
- 不重排 import、不统一引号、不重命名没动过的变量、不删死代码。
- 不引入新依赖解决小问题；能用现有依赖就用现有的。
- 新逻辑放新函数，不要重构旧函数来容纳它。
- 保留原有的错误处理风格，即使你不喜欢。

## 收尾前自检

- diff 里有没有一行跟目标无关？有就撤掉。
- 有没有格式化工具顺带改动的大片空白？撤掉或单独说明。
- 改动是否改变了对外行为？如果是，必须单独列出。

## 输出

给用户时按文件列出改动，每个文件一句话说明改了什么、为什么。最后一句说明"本次未改动"的范围（哪些相关但没动的地方），让评审者知道边界在哪。
