# 规格评审清单

评审的对象是**规格本身**，不是逐行读代码。代码只用来验证规格是否属实。

## 必查六项

1. **可判定性**
   每条约束能否被验证为是/否？"性能要好""尽量兼容"这类无法判定的句子必须打回，要求改成可测的形式（阈值、范围、枚举）。

2. **契约完整性**
   每个入口是否都写了：入参约束、返回、错误码、副作用。缺一项标缺口。

3. **边界覆盖**
   逐条对照这五项，缺哪项写哪项：空值/零值、上限（长度、数量、超时）、并发与重入、失败与重试、部分成功。

4. **隐含假设**
   规格里"默认为真但没写明"的前提。每条要求补一句"若不成立会怎样"。

5. **与实现的一致性**
   规格声称的行为，能否在代码里找到对应位置？标出规格有代码无、代码有规格无的两类偏差。

6. **变更影响**
   按这份规格实现后，哪些接口/数据结构/配置键会变，向后兼容性如何。

## 输出格式

按这个结构写，不要自由发挥：

```
## 结论
可直接进入实现 / 需修改后进入实现 / 不足以支撑实现

## 阻断问题
（必须解决才能开工的，编号列出，每条一句话）

## 缺口
| 缺口类别 | 具体位置 | 需要补充什么 |

## 建议
（不阻断的，最多 5 条）
```

## 硬约束
- 不做代码风格点评
- 不重写别人的规格，只指出缺口
- 结论必须三选一，不许写"整体还行"
